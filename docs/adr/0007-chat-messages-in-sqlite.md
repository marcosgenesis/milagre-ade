# Chat messages live in SQLite, one row each

A Project's messages move from `coordination.json` to `<project>/.milagre/chats.db`, one row per message, read and written through `node:sqlite`. A Named Link's messages move the same way, under its own folder. `coordination.json` keeps everything else: Worktrees, Chats, tasks, the shared `next_id`. Its `messages` field becomes `{ "storedIn": "chats.db", "format": 2 }`. This supersedes ADR-0003's "the saved Chat format stays unchanged" for messages.

The single file made every save encode every Chat. For a large Project that took 47 to 105 ms on the daemon's only thread, up to four times a second while a Chat ran. A row per message lets a save write only the messages that changed, and lets later work open a Chat with only its recent turns and search across Chats in SQL. That later work is in #300.

- **Ids and order stay as they were.** Message ids stay global and increasing across Chats, numbered by `next_id`. Handoff dividers, Chat ordering and pending sends depend on that. Each row also keeps the message's place in the Project's array (`position`), because array order and id order can differ: a pending message re-sent after a reply split in two. Since ADR-0009 it is a sort key with gaps rather than the array index.
- **What a save writes.** The daemon still holds every message in memory, so readers are unchanged (since ADR-0009, only the messages of Chats in use; a save leaves the rows of the others as they are). A save writes the rows whose message object changed since the last save and deletes the rows of messages that are gone, in one transaction, then rewrites `coordination.json`. A Project still on the old format moves on its first save: every row is written before the file points at them.
- **Older releases.** They don't know the format, but they read `messages` as an array and fail on anything else. So they refuse to open a moved Project, with an error, instead of showing its Chats empty. Nothing is lost, and updating fixes it.
- **Why `node:sqlite`.** It ships with Node 24 and Electron 44, so there is no native module to build and the mobile app's fingerprint is unaffected. Node 24 still labels it experimental; the daemon suppresses that one warning.
- **Considered and rejected:** one JSON file per Chat. A long Chat (5 MB) would be rewritten whole on every reply, and search would need an index of its own.
