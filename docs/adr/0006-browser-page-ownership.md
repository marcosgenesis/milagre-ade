# A Chat sees only browsers its agent started or the user attached

A Browser page belongs to a Chat on evidence, never on a name, title or URL. The host reads the OS process table: a Chromium browser process that descends from a Chat's agent process belongs to that Chat. This is meant to cover browsers started by the agent's shell commands and by its MCP servers, as long as the browser is still in the agent's process tree when the host looks. The host looks every five seconds while any agent runs, and whenever a client lists browsers. A browser that leaves the tree first (a background daemon such as agent-browser's, a shell that backgrounds Chrome and exits within seconds, or `open -a`) is not attributed and appears as an attachable browser instead. Several Chats in one Worktree each have their own agent process, so they never see each other's browsers.

Lineage is remembered once observed, because an MCP server or shell can exit while its browser keeps running. The memory lasts until that browser exits. A browser is identified by the GUID in its DevTools endpoint, which changes on every launch, together with its process ID, so a relaunched browser or a reused port never inherits an old owner.

A browser no Chat started (one the user opened with `--remote-debugging-port`, or one the agent launched through `open`) is listed under "Other browsers on this computer". Attaching it is an explicit action in the picker and adds all of its pages to the Chat it was attached from; other Chats do not see it unless they attach it too. A browser another Chat's agent started is not offered for attachment, and if lineage to some Chat appears later, other Chats' attachments to it end. Any authenticated client may list or attach for any Chat, as with every other Chat command; confined demo connections may not. Attachments live in the daemon's memory and end when the browser exits or the daemon restarts. There is no detach yet.

We considered having the agent register a target through Milagre's MCP tools when it opens a browser. Process lineage already gives that evidence without changing agent prompts or tools, and it cannot be spoofed by a tool argument. Registration remains a possible addition for browsers that leave the agent's process tree.

Only browsers with a loopback DevTools port qualify. A browser driven over `--remote-debugging-pipe` (Playwright MCP's default) has no endpoint another client can attach to; it does not appear.

Viewing never claims control. The first viewer of a page gets the free control lease, and Take control moves it, ending the previous controller's held keys and mouse button. The lease governs Milagre's viewers only: the agent keeps its own DevTools connection and can still act on the page while a person controls it. The Take control tooltip says so.
